Brightspace Integration Architecture for the LACE Learning Hub

Brightspace remains the official system of record. The LACE Learning Hub becomes a calmer, searchable learner-facing view that reads approved Brightspace data, stores searchable copies in Supabase, and sends learners back to Brightspace for official LMS activity.

Source: summary of the Brightspace API meeting, a D2L API discussion with Ahmad and Amanda, captured June 2026. Implementation closeout wrap-up is extended to August 2026. Ahmad remains the technical contact for one-off Brightspace API questions after closeout.

Build a read-mostly companion layer, not a replacement LMS.

The D2L technical guidance confirmed that this architecture is supported: Brightspace can own courses, enrollments, completion, awards, and audit trails while the Learning Hub improves discovery, search, dashboards, and learner orientation.

For implementation, treat Supabase as an indexed cache and LACE-specific data layer. Do not let Supabase become the source of truth for official Brightspace records.

Authentication Model

Decision: Use a dedicated Brightspace service user for machine-to-machine integration.

Use a service account

Create a dedicated Brightspace service user for background sync jobs and server-side API access. Do not bind the integration to Marlie's personal admin login.

Keep API calls server-side

The Learning Hub should call Brightspace from trusted server routes or scheduled jobs. Learner browsers should not hold Brightspace integration secrets.

Scopes, Roles, and Org Unit Access

Required scopes and permissions depend on the Brightspace endpoints used. The operating pattern is broad during testing, then least privilege before production.

  1. Start with enough test access to validate org units, course offerings, content structure, users, and optional awards/completion reads.
  2. Record the exact endpoints used by the Learning Hub.
  3. Before launch, remove unused scopes and role permissions.
  4. Place the service user high enough in the Brightspace org structure that access cascades to the needed child org units and course offerings.

Important inheritance note: D2L guidance confirmed that service user access at an upper org unit should cascade down, assuming the role and permissions are correct.

APIs vs. Data Hub

Source Best use LACE implication
Brightspace APIs Learner-facing search, catalog browsing, near-real-time sync, course structure, module/topic content, selected learner state. Use APIs for the actual Learning Hub experience and scheduled refresh jobs.
Brightspace Data Hub / datasets Reporting, analytics, historical exports, warehouse-style analysis, and large initial extracts. Use Data Hub for initial bulk load and analytics/reporting. Differential updates are daily; full updates are weekly.

API Areas for Version 1

Keep the first implementation narrow. The first useful Learning Hub does not need every Brightspace object.

Org Units

Hierarchy, parent/child relationships, program/course structure, and stable Brightspace identifiers.

Course Offerings

Course names, codes, descriptions, start/end dates, availability, status, and launch targets.

Content

Module and topic structure so the Hub can preview what a course contains and improve discovery.

Users, Awards, Completion

Use users only where needed for personalization. Add awards/completion if v1 needs badges, certificates, or progress views. Avoid grade-heavy design unless MLRI needs it.

Sync Strategy

  1. Run an initial bulk load, likely from Data Hub, to seed the local catalog and capture Brightspace internal IDs.
  2. Store Brightspace IDs on Supabase records so future syncs compare stable identifiers instead of names or URLs.
  3. Run scheduled incremental syncs for catalog, course, org unit, and content metadata.
  4. Run nightly reconciliation to detect items that changed, disappeared from active views, or moved lifecycle state.
  5. Only use more frequent syncs for data that must be fresh, such as awards or completion updates.

Practical cadence: nightly catalog/content refresh is enough for most discovery data. Completion or award data can refresh more frequently, around every 15-16 minutes, if the learner experience requires it.

Course Lifecycle and Versioning

Do not hard-delete local learning records just because a Brightspace course is no longer active. Course-like org units can be archived/restored; users are different and should be handled carefully if deleted.

Local statuses

Use statuses such as active, archived, retired, and hidden_from_learners to preserve history while controlling learner visibility.

Evergreen courses

Minor edits can stay in the same offering. Major revisions should become a new offering or version, with a code like LegalWriting-2026 or LegalWriting-Jun2026.

First Implementation Slice

  1. Create the dedicated Brightspace service user and assign the right role at the right upper org unit.
  2. Confirm the production OAuth/app setup and document the owner for app registration, keys, JWKS, and rotation.
  3. Sync one known course offering end to end: org unit ID, course metadata, content outline, status, and launch URL.
  4. Map synced fields into learning_items and related Supabase tables.
  5. Build the nightly reconciliation job and log sync outcomes.
  6. Review endpoint usage and reduce scopes/permissions before production.
